# 四人首轮任务分配

把A/B/C/D替换成你们四人的名字即可。每个人只先领取下面一项任务，先在共同基础工程上完成一次可独立验收的PR。

| 成员 | 首轮任务 | 主要文件 | 预计投入 | 审查者 |
|---|---|---|---|---|
| A · 前端 | [TASK-01：完善赛事详情与组合筛选](tasks/TASK-01-A-frontend.md) | `frontend/src/` | 8—12小时 | D检查推荐信息，B检查接口 |
| B · 后端与通知 | [TASK-02：实现可追踪的邮件提醒](tasks/TASK-02-B-email.md) | `backend/app/services/reminders.py`、`worker.py`、模型与迁移 | 12—18小时 | D检查失败场景，C检查后台状态 |
| C · 采集与数据 | [TASK-03：接入首个获准的官方来源](tasks/TASK-03-C-source.md) | `backend/app/crawlers/`、`services/ingestion.py` | 12—18小时，来源审核等待另计 | B检查数据与权限，A检查证据呈现 |
| D · 推荐与AI | [TASK-04：接入有证据约束的AI解释](tasks/TASK-04-D-ai.md) | `backend/app/services/ai.py`、`recommendations.py` | 10—16小时 | B检查数据边界，A检查用户文案 |

## 为什么这样拆

基架已经提供登录、基本权限、规则推荐、订阅和站内提醒，因此四个人可以直接从四个不同方向扩充，不必各自重建后端。

- A把用户页面做完整，复用当前API。
- B复用已有提醒计划与Outbox，补外部触达。
- C复用离线适配器与通知版本，把演示数据扩展到合规真实来源。
- D复用现有理由代码和规则基线，增加模型能力。

## 第一次协作顺序

1. 四人各自先运行README的五分钟演示。
2. B确认共享模型及迁移约定；A和D确认推荐理由响应结构；C和B确认通知输入结构。
3. 共同确定首轮完成日期，然后各自建分支，不必等待其他任务全部完成。
4. 第二个工作日各开Draft PR；完成后按任务书验收。
5. 合并前四人共同完成：查看来源证据→修改画像→推荐→订阅→通知的演示。

四份任务均可直接复制成GitHub Issue；此处没有自动创建远程Issue或仓库。

## 首轮之外的共同待办

- 正式账号注册、密码重置、登录限流和邮箱验证。
- 完整来源审核后台、跨来源赛事归并、PDF处理。
- 安静时段、提醒偏好与邮件摘要。
- 来源域名全局限速与多机器Worker演练。
- 正式部署的TLS、备份、权限与故障恢复验证。

这些不应被误认为已由当前基架完成。优先完成首轮四个PR，再按原八周计划扩充。
