# 四人协作约定

1. 每人先领取`docs/TEAM_TASKS.md`中的一个首轮任务，名字可替换成真实姓名。
2. 一个任务一个短分支，如`feat/a-detail-filters`。首轮只改自己负责的主要模块。
3. 共享的`models.py`、`schemas.py`、API路径和响应结构先在Issue里约定，再修改；新增字段提交Alembic迁移。
4. 尽早开Draft PR，说明已完成和待完成部分。至少一名非作者审查，必要检查通过后Squash合并。
5. `main`保持可演示；不直接提交密钥、真实个人数据、数据库、受限制网页、依赖目录。
6. 一次PR尽量只解决一个可独立验收的问题。每次PR说明行为、验证和剩余限制。
7. 每周至少合并并演示一次完整流程。不要到最后一周才第一次联调。
8. 默认测试使用本地样本。真实网站测试必须显式开启、通过来源准入，不能成为普通CI的联网步骤。

GitHub仓库建议由一位同学创建后邀请其他三人；建立`Backlog / Ready / In Progress / Review / Done`看板，手动将四份任务书转为Issue。

推荐分支保护：至少1人审查，CI通过，禁止强推与删除主分支。按账户方案确认可用功能。
